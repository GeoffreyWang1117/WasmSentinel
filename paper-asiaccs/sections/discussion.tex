\section{Discussion}
\label{sec:discussion}

\paragraph{Where the CPU goes, and the lever that moves it.}
Across E3, E4 and E5 the same picture repeats: the sandbox boundary costs
a few microseconds per call (\eTwoEngineOverheadUs{}~\si{\micro\second}
empty, \eTwoMlRawUs{}~\si{\micro\second} for a real rule on a process
event), but \sys spends \eThreeDetectPFiftyBinTenKRf{}--\eThreeDetectPFiftyJsonOneKRf{}~\si{\micro\second}
per syscall event and up to \eFourCpuPgWs{}\% of a core under PostgreSQL,
where Falco spends \eFourCpuPgFalco{}\% and Tetragon \eFourCpuPgTetragon{}\%.
Two decisions, neither of them forced by the sandbox, produce that gap.
First, \sys delivers every collected event to every rule; Falco and
Tetragon filter in the kernel and most events never reach user space. A
rule could declare which event types and syscalls it wants, and the
collector could install that filter in eBPF; the fixed-record design makes
this a map update rather than a code change. Second,
\texttt{ml\_detector} recomputes a 64-dimensional feature vector over its
100-event window on every event. Most of those features are counts and
bigram frequencies that can be maintained incrementally in $O(1)$ per
event. We did neither here because this paper's question is what the
boundary costs, and an optimised rule would have made the boundary look
cheaper than it is; we report the lever so that the reader can price it.

\paragraph{What the binary encoding buys.}
The fixed-layout record cuts a real rule's per-event cost by about half
(E2) and raises the pipeline's saturation throughput by
\eThreeBinGainPctRf{}\% (E3). It does so by removing a parse, not a copy:
the event is still copied into linear memory. We measured a variant of the
rule that rebuilt a JSON document from the record inside the guest, and
it gained nothing. Encodings matter only when the rule consumes them
directly, which argues for giving rule authors a field-access library
(\texttt{EventFields}) rather than a format.

\paragraph{The sandbox is model-agnostic, and the protocol showed it.}
The first version of this evaluation shipped only the MLP, and E1 said
plainly that a random forest on the same 64 features was the better model
(\eOneAuprcRf{} against \eOneAuprcMlp{}). Because the evaluation already
scored every trace through the module, replacing the model was a matter of
giving the module a second loader: a tree ensemble is a table of thresholds
and child indices, \rfNodes{} of them here in \rfKiB{}~KiB, walked in
place from the module's data segment. The one subtlety is numeric.
scikit-learn stores thresholds in float64 and compares float32 features
against them; the exporter rounds each threshold down to the nearest
float32, and we checked with an SMT solver (Z3, over all float32 features
and finite float64 thresholds) that this preserves every comparison, which
is why the forest in Wasm reproduces scikit-learn to
\eOneWasmSklearnMaxDiff{} rather than approximately. The forest is now the
number we attach to \sys (\eOneAuprcRfWasm{}), it costs less per event
than the MLP did (Table~\ref{tab:e3}), and it is the module's default deep
path, the one E4 and E5 were measured with; the MLP stays in the module
behind an init option. What we claim for
E1 is still the protocol rather than the number: a reader can swap in the
next model and get the module's own accuracy for it the same way.

\paragraph{Per-event alerting is not an operating point.}
E1 scores whole traces offline. The deployed rule scores a sliding window
on every syscall event and raises a level whenever the score crosses a
threshold, and on normal ADFA-LD traffic that produces an alert on a
substantial fraction of events; on the live traffic of E4 it was
\eFourWsAlertPctNginx{}\% of events under nginx and \eFourWsAlertPctPg{}\%
under \texttt{pgbench}, whose syscall numbers the ADFA-trained STIDE
database has never seen. Turning a per-event score into a
deployable alert needs aggregation over a window or a process lifetime,
which is a rule-design question we have not evaluated; the E5 detections,
which are per-event by nature, are unaffected.

\paragraph{Differences that are semantic, not performance.}
Writing the same detection three times (E5) surfaced hooks that see
different things: Tetragon's LSM-based file hook misses an open that fails
its permission check, while a syscall-entry hook sees the attempt. \sys's
collector takes the syscall-entry view for opens and the kernel-function
view for TCP, and sees IPv4 addresses only. Such differences decide what a
rule \emph{can} detect before any question of cost, and a fair comparison
has to configure each system to the same semantics, as we did.

\paragraph{Limitations.}
Our accuracy evidence is one dataset, ADFA-LD, recorded on a 2013 Ubuntu
system with i386 syscall numbers that differ from the x86-64 numbers the
live collector emits; the feature set we inherited mixes ABIs, and we kept
it because the trained weights depend on it. We did not evaluate evasion:
no mimicry sequences or adversarial inputs were tried against either model,
and the three E5 actions are hand-written triggers, not an attack corpus.
The isolation experiment is a set of eleven attempts, not a proof; a
runtime bug or a side channel is out of scope. The timing experiments ran
on a shared machine with a background load we report but could not remove,
so absolute throughputs carry noise that the paired intervals only partly
capture; under \texttt{pgbench} the daemon was saturated and dropping
events (\S\ref{sec:eval:e4}), so its cost there is a saturated monitor's,
and whether the levers above restore headroom is untested. Falco and Tetragon were run
with their default settings and our policies; an expert configuration of
either would likely lower its cost. Finally, \sys is on wasmtime-go~v17;
newer runtimes change the constants in E2 but not, we expect, the shape of
the results.
